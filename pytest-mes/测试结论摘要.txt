--------------------------------------------------------------------------------

    模块            用例数   说明
    登录与权限      6        未登录拦截、验证码、越权、会话失效、会话存储切换
    仓库管理        7        编号生成与回收、库位容量、级联删除、取整损失
    库存管理        6        可用量计算、删除约束、唯一索引、零库存自动清理
    工单下达        16       参数校验、容量校验、BOM 展开/防环/共享子件、跨库位拆分
    工单确认        7        入库/出库确认、重复确认、状态校验、流水编号

    并发            3        并发锁定、并发确认、并发取号

    口径说明（重要）：
      一个测试函数可能覆盖多个用例编号，例如"入库确认"一条测试同时验证
      WO-001 与 CF-001，因此 29 个测试函数 ≠ 29 条用例。
      简历与面试统一按「46 条设计 / 24 条自动化（29 个测试函数）/ 22 条手工」讲，
      不要讲成"46 条全部自动化"，仓库里 collect 出来只有 29 个测试。

    22 条手工用例清单（尚未自动化，按模块）：
      登录权限    AUTH-002 验证码错误、AUTH-003 验证码为空、
                  AUTH-004 越权调用写接口（低权限账号）、AUTH-006 会话存储切 Redis
      仓库管理    WH-002 库位数量为空默认 0
      库存管理    INV-004 唯一索引防重复入库、INV-005 空库位编码、INV-006 扣到 0 自动清理
      工单下达    WO-005 BOM 递归展开、WO-007 BOM 间接循环（A→B→A）、
                  WO-008 菱形 BOM 共享子件、WO-009 跨库位拆分、WO-011 BOM 自引用、
                  WO-012 脏数据造环防死循环、WO-013 库位级容量、WO-014 多物料共享库房容量、
                  WO-015 库位库存计入库房容量、CF-007 修改数量后锁定重算
      工单确认    CF-004 需求已发放再确认、CF-005 流水编号格式与唯一、CF-008 发料超锁定
      数据一致性  CON-001 库存 / 流水 / 锁定量三方对账

    这 22 条为什么先手工（面试可讲，按你的实际情况删改）：
      · BOM 系列（WO-005/007/008/011/012）需要先在库里造多级 BOM 数据，
        造数与清理成本高于一次接口调用，用 SQL 脚本 + 页面手工验证更快；
      · 越权（AUTH-004）需要第二个低权限账号，当前测试环境只有 admin；
      · 会话存储切换（AUTH-006）要改 spring.cache.type 并重启应用，
        属于环境级验证，不适合放进日常回归的自动化用例集；
      · 三方对账（CON-001）手工跑一遍即可，自动化版本正在补。

三、缺陷清单（2 个，均已修复并回归）
--------------------------------------------------------------------------------
BUG-001（严重）库房容量校验未汇总，跨物料 / 跨库位均可绕过
    现象：库房容量 100，物料 A 入 100 后换物料 B 仍可再入 100（合计 200）；
          三库位各存 33 后再以“只选库房”入 100 也被放行（合计 199）。
    根因：validateInboundCapacity 统计时带了 materiel_code 与精确 location_code 两个条件，
          容量实际只是“单物料 + 单位置”的上限。
    修复：去掉物料条件；库房级统计全部库位 + 库房级库存；提示文案同步调整。
    回归：WO-003 / WO-013 / WO-014 / WO-015 全部通过。

BUG-002（一般）并发创建工单取号冲突，直接返回数据库异常
    现象：20 并发创建 → 成功 5 / 失败 15，失败返回
          Duplicate entry 'GDxxx' for key 'sp_work_order.uk_order_code'。
    根因：generateOrderCode 采用“查最大号 + 1”，并发下算出相同编号，且无重试。
    修复：改为 sp_sequence 表原子自增（UPDATE ... LAST_INSERT_ID），
          Controller 保留唯一键重试作为兜底；异常不再透传给前端。
    回归：20 并发创建 → 成功 20 / 失败 0。
